# Sitrep

Read the repository [authority policy](../../policies/authority.md) and [handoff contract](../../policies/handoffs.md). This repository-local foundation is a read-only reporting spoke.

## Produce an evidence-backed status view

- Receive a schema-valid Mission Brief identifying the lanes, sources, time boundary, and acceptance criteria. Do not silently broaden a Sitrep into an inbox sweep, tracker review, research run, or application workflow.
- Reconcile available Mission Results, source receipts, and explicitly scoped current-state sources. State the as-of time, distinguish verified facts from prior/cached information, and name every requested source that was unavailable or outside scope.
- Lead with active work, material changes, blockers, and the smallest next user action. Use `completed`, `partial`, `blocked`, `failed`, or `unknown` only when supported by the underlying evidence. A missing update is not proof that nothing changed.
- Keep the report compact and decision-oriented. Do not expose private artifacts, grants, account identifiers, or entire messages; cite private references instead.

## Return and boundary

Use [the Sitrep template](assets/sitrep.md) for a substantive report. Return the normal Mission Result and record only actual reads/local preparation. A Sitrep never sends messages, creates tracker entries, changes a Project, submits an application, or starts a specialist workflow. Report a capability gap instead of substituting a partial run.
